## 2. Диагноз: где текущий дизайн ломается

### 2.1 Критично: dual-CLI не даёт разнообразия

Из `AGENTS.md` репозитория Kilo Code, раздел Products:

> `packages/opencode/` — Core engine. TUI, kilo run, kilo serve.
> **Fork of upstream OpenCode.**

Подтверждение со стороны: обзоры CLI-агентов 2026 описывают Kilo как
«форк Roo Code, чей CLI сам построен на OpenCode»
(pinggy.io/blog/best_open_source_cli_coding_agents).

**Следствие.** Kilocode и Opencode — один агентный рантайм, один цикл tool-use,
одна логика поиска. Различаться могут только модели под капотом.
Cross-summary «общее / различия / на что обратить внимание» из MAP.md
сравнивает почти близнецов.

Это ровно тот риск, который владелец сам зафиксировал в премортеме N3 как
**«redundancy theater»**. Он реализовался не в процессе, а на этапе выбора
инструментов — до первой строки кода.

### 2.2 Дублирование вместо декомпозиции

`dispatcher.py` шлёт `task_content` целиком обоим агентам (строки 52-57).
Литература 2026 однозначна: multi-agent выигрывает на **параллелизуемой**
работе с независимыми подзадачами, и проигрывает на дублирующей.

- Google Research: +81% на параллелизуемых задачах, **−39…−70% на
  последовательных** (по обзору augmentcode.com/guides/single-agent-vs-multi-agent-ai).
- Stanford/Contextual AI, arXiv 2604.02460: при равном бюджете токенов
  single-agent **стабильно не хуже** multi-agent на multi-hop рассуждении.
- Anthropic: multi-agent тратит **~15× токенов** относительно чата.

Вывод: текущая схема платит цену multi-agent, не получая его выгоды.

### 2.3 Что в проекте хорошо (не выбрасывать)

- `MAP.md` / `MAP-phase1-hardening.md` / `MAP-phase2.md` — дисциплина картирования.
- Тикеты с resolution и обоснованием отклонённых решений (пример: отказ от
  `pydantic-settings` с аргументацией scale mismatch).
- Явные премортемы и запись degraded-mode правил **до** реализации.
- `metrics.json`, provenance, intake gate, `_clean_env`, `os.killpg`.
- Правило «prefer false NEEDS_WORK over false APPROVED» — редкая зрелость.

Это уровень мышления выше среднего пет-проекта. Проблема не в качестве
инженерных решений, а в том, что они приложены к треснувшему фундаменту.

Без ключа работает, но по IP-лимиту. **Риск `429` на 10–30 страницах прогона.**

### 4.2 Единственная статья расхода — MiniMax M3

Три независимых источника сходятся:

| Позиция | Цена / 1M токенов |
|---|---|
| Input (≤512K контекст) | **$0.30** |
| Output | **$1.20** |
| Cache read | $0.06 |
| Input (>512K) | $0.60 / output $2.40 |

Источники: devtk.ai/en/models/minimax-m3, minimax-ai.chat/pricing,
pricepertoken.com, aiapiprices.com — совпадают.

**Оценка одного research-прогона** (~200K input + 30K output):

```
200 000 / 1M × $0.30  = $0.060
 30 000 / 1M × $1.20  = $0.036
                      ─────────
                        ≈ $0.10
```

**~$0.10 за прогон. 10 прогонов ≈ $1.** Порог входа не финансовый.

Для справки, M3 против фронтира: input в 8.3× дешевле Claude Opus 4.7,
output в 10.4× дешевле, контекст 1M против 200K.

## 5. Риск LLM-судьи (для Phase 2)

Наивная схема «один промпт → оцени по критериям → json.loads» ломается.
Доказательная база 2025–2026:

- **arXiv 2606.19544** — крупнейшая проверка: 21 судья, 9 провайдеров,
  ~541 000 оценок. Высокая test-retest надёжность (>0.95) **сосуществует** с
  тяжёлым позиционным смещением (>0.10) у двух продакшн-судей.
- **arXiv 2406.07791** (IJCNLP 2025) — 15 судей, ~150 000 оценок:
  позиционное смещение **не случайно**, зависит от судьи и задачи.
- **RAND (2026)** — ни один судья не надёжен равномерно; фронтир-модели
  дают **>50% ошибок** на JudgeBiasBench.
- **arXiv 2512.16041** — **authority bias**: модель выше оценивает ответ
  со ссылками, **даже если ссылки выдуманы**. ← прямое попадание в наш кейс.
- **EMNLP 2025** — multi-agent debate **усиливает** смещение после первого раунда;
  meta-judge устойчивее.

**Что работает (arXiv 2506.13639):**
1. Явные критерии + reference answer в промпте — главный вклад в согласие с людьми.
2. Sampling-based scoring с усреднением > один жадный прогон.
3. CoT почти не помогает, если критерии детальные — экономия токенов.
4. Самогенерируемые рубрики снижают несогласованность на ~16% (arXiv 2512.16041).
5. Спот-чек: сверить ~10 вердиктов с человеком. **Расхождение >20–25% = рубрику переписать.**

**Практический вывод для Layer A:** раз судья вознаграждает ссылки не проверяя их,
проверять должен **детерминированный код**: HTTP-статус каждого URL, наличие
цитат, покрытие утверждений. Это ~40 строк и ловит галлюцинации-источники
без единого вызова LLM.

## 7. Рекомендуемый план (Вариант B)

### Этап 1 — Замер (один вечер, ~$1)

```bash
git clone https://github.com/bytedance/deer-flow.git && cd deer-flow
make config
cp .env.example .env        # вписать MINIMAX_API_KEY=...
# в config.yaml (~строка 417) раскомментировать блок minimax-m3
make docker-init && make docker-start
# http://localhost:2026
```

Задать **тот же вопрос**, что в `tasks/task.md`. Заполнить таблицу
в `docs/research/deerflow-trial.md`.

> Перед серьёзными прогонами включить в `config.yaml`:
> ```yaml
> token_budget:
>   enabled: true
>   max_tokens: 200000
> ```
> Это тот самый «cost ceiling», который требует MAP-phase2.md.

**Что менять в `config.yaml` (~строка 417) — снять `#` с блока:**

```yaml
models:
  - name: minimax-m3
    display_name: MiniMax M3
    use: deerflow.models.patched_minimax:PatchedChatMiniMax
    model: MiniMax-M3
    api_key: $MINIMAX_API_KEY
    base_url: https://api.minimax.io/v1
    temperature: 1.0
```

Отступы в YAML критичны: `- name:` идёт с двумя пробелами.
Поиск трогать не надо — DuckDuckGo включён по умолчанию.
Если VPS удалённая: `ssh -L 2026:localhost:2026 user@vps`.

**Чек-лист замера (заполнить руками):**

| Критерий | наш dispatcher | DeerFlow |
|---|---|---|
| Время прогона | | |
| Кол-во источников | | |
| Ссылки реальные (открыть 3 шт.) | | |
| Отвечает на вопрос или «вода» | | |
| Нашёл то, чего я не знал | | |

### Этап 3 — Куда вкладываться при любом исходе

Три вещи, ценные независимо от выбора ядра:

1. **Детерминированная проверка цитат** (~40 строк): каждый URL → HTTP-статус.
   Против authority bias. Это честный Layer A.
2. **Layer B по правилам из §5**: судья другого семейства, явная рубрика,
   3 прогона с усреднением, спот-чек на 10 примерах.
3. **Автономность и дисциплина**: watch-режим, история прогонов, `metrics.json`,
   MAP/тикеты. **Этого нет ни у DeerFlow, ни у GPT Researcher.** Реальная ниша.

### Этап 4 — Только если упрёшься

Порядок важен: **не оптимизировать то, что ещё не стало узким местом.**

| Симптом | Решение |
|---|---|
| `429` от Jina в логах | Crawl4AI (75k★, Apache-2.0, self-hosted, «no third-party API key») |
| Crawl4AI жрёт память | Lightpanda (32.7k★, легче, CDP+MCP) |
| Нужен максимум качества | NVIDIA AI-Q как референс архитектуры |

**Про Lightpanda — важные оговорки:**
- Напрямую как `web_fetch` **не подключается**: DeerFlow'овский browserless-клиент
  ходит в REST `{base_url}/content`, Lightpanda говорит по CDP на `ws://:9222`.
- Обходные пути: (а) `lightpanda mcp --port 9223` → подключить как MCP-сервер;
  (б) `lightpanda fetch --dump markdown` → свой 30-строчный провайдер.
- **Лицензия AGPL-3.0** (у DeerFlow MIT). Для себя — неважно. Для публичного
  сервиса — требует открыть исходники.
- Их же README: *«Lightpanda is in Beta... You may still encounter errors or crashes»*.
  CORS не реализован.
- Телеметрия включена по умолчанию: `LIGHTPANDA_DISABLE_TELEMETRY=true`.
